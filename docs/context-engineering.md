# 上下文工程：讓 AI 記得對的事

> 有意識地決定 AI 每一輪「看得到什麼」，用最少的資訊換到最準的產出。

## 學習目標

完成本單元後，你能夠：

1. 說明 AI 每輪回覆實際看到的上下文由哪些部分組成。
2. 為任務挑選最小且相關的檔案，而不是把整個專案貼進對話。
3. 建立 `AGENTS.md`／專案說明檔，把長期規則與短期需求分開。
4. 在對話變長時，用摘要與重新對齊（re-anchor）維持準確度。
5. 辨識並移除過時、矛盾或無關的上下文，避免 AI 依錯誤前提作答。

## 前置知識

- [串接 API 與處理資料](./api-and-data.md)
- 你已經有分層的專案結構與 `tests/`，知道哪些檔案是核心、哪些是產物。

## 為什麼重要

AI 沒有記憶，它每輪只看得到你當下提供的內容。上下文太多會稀釋重點並增加出錯與幻覺的機率，太少則讓 AI 靠猜測補洞。真實開發中，同一個需求在「貼對三個檔案」與「貼三十個檔案」下的產出品質差距明顯。上下文工程就是把「決定 AI 看什麼」變成一個有意識的動作：只給必要的檔案、明確的規則、當前的目標，並在對話偏移時主動收回焦距。

## 核心內容

### 小節一：AI 每輪看到什麼

逐輪對話中，模型實際收到的內容大致由四層組成：

```text
[1] 系統與工具規則（模型與環境設定，你多半無法改）
[2] 長期專案規則（AGENTS.md 等，跨對話生效）
[3] 對話歷史（先前訊息與工具輸出，會佔用視窗）
[4] 本輪輸入（你的訊息 + 你貼的檔案內容）
```

第 [2] 與 [4] 層是你最能控制的。**原則：把「不變的規則」放進 [2]，把「這次要改什麼」放進 [4]。** 不要把每次都要重複的規範塞進每輪訊息。

### 小節二：只給相關的檔案

給上下文前先問：**這個任務要動到的檔案有哪幾個？它們依賴什麼？** 只貼這條依賴鏈，通常 3～5 個檔案。

以「在 `core.py` 新增 `delete_task`」為例，最小上下文是：

```text
相關檔案（只列這些，請勿假設其他檔案內容）：
- src/tasklite/core.py（要修改）
- tests/test_core.py（要補測試）
- src/tasklite/cli.py（只需知道它如何呼叫 core）

任務：新增 delete_task(tasks, task_id)，找不到 id 時拋 KeyError。
限制：不改 storage.py，不新增檔案，不回傳 None。
```

不確定該給哪些檔案時，先請 AI 反問你：「要完成這個任務，你需要看哪些檔案？請列出清單，不要先寫程式。」這一步常能省下大量來回。

### 小節三：用 AGENTS.md 放長期規則

長青規則寫成專案根目錄的 `AGENTS.md`（有些工具也用 `CLAUDE.md`），讓每輪自動帶入。內容要短、可執行：

```markdown
# AGENTS.md

## 專案
- 語言：Python 3.11+，僅用標準函式庫。
- 結構：src/tasklite/{cli,core,storage}.py，測試在 tests/。

## 規則
- core.py 保持純函式，不得 import json 或開檔案。
- 所有新函式都要有 unittest 測試，錯誤路徑至少一個。
- 執行測試：python -m unittest discover -s tests -v
- 不要自動執行 git commit、git reset 或任何推送。
- 回覆時列出你動過的檔案與原因。

## 風格
- 不使用第三方套件，除非先說明安裝指令與版本。
```

**待確認**：不同 AI 工具讀取專案說明檔的檔名與位置不同，請查閱你所用工具的文件。

### 小節四：對話變長時重新對齊

對話越長，早期訊息越容易被新內容淹沒，AI 可能開始依據已經作廢的決定作答。察覺到偏移時，用一段「現況摘要」重新對齊：

```text
【重新對齊】
目前的決定（以此為準，忽略先前相反的說法）：
1. 任務資料用 JSON 檔儲存，不用資料庫。
2. core.py 維持純函式，storage.py 負責 I/O。
3. 目前目標：完成 delete_task 與其測試。

請確認你已理解這三點，再繼續。
```

若對話已長到難以收拾，最乾淨的做法是**開新對話**，把 `AGENTS.md` 加上一段精簡的現況摘要帶過去。新對話的上下文更乾淨、成本更低。

### 小節五：移除壞上下文

壞上下文比沒有上下文更危險。常見三種：

| 類型 | 例子 | 處理 |
|---|---|---|
| 過時 | 舊版 API 規格、已刪除的函式 | 明確標註「以下已作廢」或直接移除 |
| 矛盾 | 前文說用 SQLite，後文說用 JSON | 重新對齊並宣告唯一版本 |
| 無關 | 一次貼上整個 `node_modules` 或日誌 | 只保留與任務相關的片段 |

一個實用習慣：貼長內容時加上標記，說明它是否仍有效。

```text
以下是「已作廢」的舊設計，僅供對照，請勿採用：
- ~~使用 SQLite 儲存~~
```

### 小節六：用摘要壓縮，而非硬塞

需要保留長文件或長紀錄時，先請 AI 產生結構化摘要，再把摘要當上下文：

```text
請把以下規格整理成 5 條要點，保留欄位名稱與限制，去除舉例與客套。
輸出格式：
- 目標：
- 必須符合：
- 明確禁止：
```

摘要的好處是同時降低 token 成本與降低干擾。但**摘要會遺失細節**，若任務涉及精確欄位或數值，仍應把原始段落一併附上。

## 常見坑

| 錯誤 | 原因 | 正確做法 |
|---|---|---|
| 把整個專案貼進對話 | 以為給越多越準 | 只給任務依賴鏈上的 3～5 個檔案 |
| 每輪重述同樣的規則 | 沒用長期規則檔 | 把不變規則寫進 `AGENTS.md` |
| 對話很長仍不重新對齊 | 舊決定被新內容淹沒 | 用現況摘要明確宣告有效版本 |
| 同時保留矛盾指示 | 未清理舊上下文 | 標記作廢或直接移除，只留一份有效版本 |
| 只給摘要就要求精確輸出 | 摘要已遺失細節 | 精確任務附上原始段落與欄位 |
| 讓 AI 假設未提供檔案的內容 | 未限制、AI 自行腦補 | 明寫「請勿假設其他檔案內容」 |
| 上下文含秘密或真實金鑰 | 直接貼環境檔 | 只貼結構，秘密用 `<你的金鑰>` 佔位 |

## 動手練

**練習**：為一個真實任務設計「最小上下文包」，並比較有無 `AGENTS.md` 的差異。

1. 在 `tasklite/` 根目錄建立 `AGENTS.md`，內容依「小節三」改寫成你的專案版本（至少 5 條規則）。
2. 在一個新對話中，只貼「小節二」那種最小上下文，請 AI 新增 `delete_task`。記錄它問了幾個澄清問題、動了哪些檔案。
3. 開另一個新對話，改貼整個 `src/` 與 `tests/` 的所有檔案，做同一個任務。比較兩次的產出與你的閱讀負擔。
4. 在任務進行到一半時，故意加入一句與先前矛盾的指示（例如「改用 SQLite」），觀察 AI 是否混亂；接著用「小節四」的重新對齊段落修正。
5. 把兩次實驗的差異寫成 3 條自己的心得（例如「何時該多給檔案」）。

**提示**：這個練習的重點不是「哪一次一定比較好」，而是觀察上下文改變時，AI 的澄清問題數量、動到的檔案範圍與錯誤率的變化。把觀察到的現象寫下來，比記下結論更有用。

## 完成檢核標準

- [ ] 我能說出 AI 每輪看到的四層上下文分別是什麼。
- [ ] 我的專案有 `AGENTS.md`，內含可執行的規則（測試指令、結構限制、禁止動作）。
- [ ] 我能在提示中列出「只列這些檔案，請勿假設其他檔案」。
- [ ] 我曾在對話偏移時使用重新對齊摘要，並確認 AI 回到正軌。
- [ ] 我能辨識並移除至少一種壞上下文（過時／矛盾／無關）。
- [ ] 我不會在上下文或提示中貼上真實金鑰或秘密。
